# Actual official, role workload and next-pitch gate

This is a standalone, scheduled verification pipeline. It must execute only after a genuine physical-end gate succeeds and supplies its checked closed artifact. The construction/pre-end backup is insufficient. Preparation does not assert that any physical end, official application or subsequent artifact stage has passed.

## Required input

The physical owner must provide the exact end Source ID, a new closed backup path and SHA-256, the successful gate's terminal/evidence file and SHA-256, source commit/manifests and original input lineage. The current minimal producer plans Source `physical-end` and an `ended-chain.sqlite` output, but no such output is usable before its successful terminal receipt. Its artifact must contain the matching real persisted end and seal, survive the owner's all-close/reopen/retry checks, and have absent/empty WAL. An inserted end row, a derivable proposal or a file hash alone is not physical completion authority.

The official helper authenticates the persisted closed end and fence on its own SQLite connection and imports the original call/rule references. The wrapper records the authenticated end reference returned by that helper. The external producer report is separately pinned by its file hash; its final report schema still must be checked against the producer's actual completed output before launch.

Freeze the selected source only after this helper/wrapper cut has been checked and reviewed. The wrapper must run from the frozen source's `tools/verification/actual-live-pipeline` directory. Source remains path-configurable in `run-config.template.json`; a different worktree or Source commit needs a newly bound manifest. `freeze-source.mjs` records every tracked file plus generated files under `src`. Node binary and vite-node entry hashes are separately required.

## Launch contract

After scheduling, fill every placeholder in `run-config.template.json`, including explicit RSS, wall-time and available-memory budgets. Do not treat the template as approval to choose those budgets. The measured Node26 cap is 1024 MiB old space / 1120 MiB total V8 heap. The launcher exports `NODE_OPTIONS`, and a preload plus the actual helper-execution process independently record and check the total heap limit. A launcher flag or parent-process receipt is insufficient: Vitest 2 previously stripped the parent CLI limit from fork workers. This standalone runner uses vite-node directly; it does not use test discovery or a Vitest worker pool.

The scheduled command is:

`bash SOURCE_ROOT/tools/verification/actual-live-pipeline/run-pipeline.sh /absolute/frozen-run-config.json`

The shell nonblockingly holds both historical Native locks, enforcing the current one-heavy-process policy. The supervisor validates both inherited descriptors against their exact file identities and passes them to the actual Node process, which records and checks its own retained descriptors. Thus an unexpected supervisor exit does not release the locks while its heavy child remains alive. The Python supervisor owns one Node process group, samples aggregate RSS for that group, enforces explicit wall/RSS budgets, terminates/reaps its process on failure and verifies the actual execution PID's heap and lock receipts. It preserves logs, stage receipts and databases; it never automatically retries or deletes a failed stage. A supervisor failure, guard termination, missing runtime receipt or missing successful terminal result is not a pass.

## Observability and setup cost

Every trigger fault now uses the already reviewed `witnessSqliteWrite` descriptor interceptor, with the exact owner INSERT SQL and a small writer-local mutation observation. It must observe the real INSERT return after its trigger before fault evidence is emitted. Generic early exceptions cannot stand in for rollback coverage. It holds only target statements and restores in finally. Do not add a global `vi.spyOn(DatabaseSync.prototype, 'prepare')`: its result history was shown to retain unrelated native statements. The wrapper refuses an obvious global prepare spy before/after helpers.

Each physical/official/role setup is performed once, then reused through a closed SQLite backup. There is no rerun of the original pitch/capture/decision construction between downstream stages. Fault triggers are removed after rollback on the same disposable stage copy. Required stale/recovery probes remain separate copies. Immediate retry and close/reopen retry are intentional durability checks. Owner authentication at each fresh read, writer transaction boundary, retry and reopen must not be removed to reduce cost; prepared-statement pooling is not authority to cache validation results across these boundaries.

Each stage emits a `status: passed` receipt only after the actual helper returns, its fault evidence is checked, closed output hashes are verified and durable row deltas match. Helper invocation counts are distinct from committed application/activity/actor/pitch counts. One new persisted physical-pitch action is not a claim that deterministic verification never re-executed physical calculations internally. Successful official and workload receipts survive a later failure; unfinished later outputs are not certified closed or reusable. A subsequent continuation must explicitly bind the successful prior receipt and artifact rather than repeat the original physical setup or call a partial stage complete.
