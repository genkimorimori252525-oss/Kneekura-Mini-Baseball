# 球場制作の作業手順

## 新しい球場・装飾を作る

1. 球場制作部README、最新CURRENT、制作指針、本人の最新要件を読む。凍結した内野・既存PNG・物理・公式結果と、編集可能な外野距離・壁高・建築・色を分ける。仕様を推測で公式ルールへ昇格させない。
2. 同じ視点の参照と実描画を並べる。完成イメージと実装を区別し、外形、構造、色、投影、遮蔽、細分、照明のどこが違うか絞る。
3. 原画と加工素材の両方を保存する。生成加工なら使用ツールと目的、加工指示、採用/不採用を残す。狼は採用された金色光点の素材を使い、拒否された手描き輪郭へ勝手に戻さない。
4. world座標の面・UV・支持構造を定義する。まず粗い面で全カメラから確認し、細部のためだけに構造を過分割しない。球場全景用と投手用に別の矛盾する建築を作らない。
5. 素材を下地へ合成し、同じ光点へ変換する。精密部分は素材の輪郭と小さな周辺だけを細分。壁面文字や模様にも同じ技術を再利用する。密度や発光を最大にすること自体を目的にしない。
6. 入力検証・取消・やり直し・JSON・保存・inspectまで接続する。無効入力を黙って丸めたり、未確定編集を再描画で捨てたりしない。欠落optional項目はfallbackし、旧JSONを自動移行しない。
7. 設計室の静止cacheと試合中の動的観察を区別し、素材前処理を毎frame繰り返さない。群衆を個別の巨大actorリストへ展開しない。停止・タブ非表示・無観客で不要なtimerを止める。
8. verify/test/buildに加え、9視点、近/遠/斜め、回転、屋根開閉、満員/無観客、保存再読込、320/390幅を必要範囲で確認する。精密点が屋根や選手を貫通しないか、別のray/triangle実装で確かめる。
9. 画像を実際に見て採否を決める。テスト期待を変えるときは、意図した仕様変更かテストの欠陥かを説明する。原FAILと不採用画像を削除しない。
10. 変更対象、理由、代案、影響、実検証、未検証、復旧方法を専用CURRENTにcheckpointする。共有Coreや別チャットのCURRENTを上書きしない。人間の美術承認と技術PASSは別々に記録する。

## このセッションで得た採否

| 試した方法 | 結果・次へ残す知見 |
|---|---|
| 狼を手描きで置き換える | 原画と違うため不採用。採用参照を加工して使う |
| ロゴだけ精密な線や画像を貼る | 周囲の光点と違う。素材から光点へ変換する |
| 大きい矩形だけ細分 | 密度の矩形が浮く。輪郭距離maskで必要最小限へ |
| 個別観客を細かく大量生成・間引く | 密な縞や無観客に見えた。共有群衆タイルへ |
| 長いLED線 | 人体との比率が不自然。実寸7cmと発光点へ |
| 2拍/2拍/3拍という解釈 | 本人が訂正。2コマ動作2周＋3コマ動作1周 |
| 固定高密度・強発光の壁面狼 | 遠いのに鮮明すぎる。投影サイズに応じたsampleへ |
| 距離で狼を強く減光 | 消えやすいため撤回。明るさを保ち軽いぼけへ |
| 葉の移動だけの屋根 | 外装から角が張り出す。外形から開いた葉の幅を制約 |
| スコアボードOFFで視点fallback | カメラが飛ぶ。構造の照準点を安定保持 |
| 技術PASSだけで完成扱い | 不十分。実画像確認と本人の完成確認を区別 |

## 改善の余地

異方性sample、LODの連続性、よりよい屋根曲面、素材の前処理とcacheの節約、端末別の情報量調整は比較してよい。共通のworld構造・光点の質感・遮蔽・編集の可逆性を維持し、旧手法より良いという証拠を添える。現在の係数やファイル分割を永久の唯一解にしない。

未測定の実機スマホ/Safari性能や通常試合の公式接続を、制作法の改善だけで完了としない。通常試合へ導入する段階では、壁衝突・HR・ホームランキャッチ・守備予測・イベント・表示盤を正史Coreと接続して別途検証する。
