# 球場制作の技術解説

この文書は実際のソースを説明する。提案を実装済みと混同しない。個別の試行と採否は同梱の `docs/ballpark-studio/CURRENT-*.md` と `PLAN-*.md` に保存し、最新状態は球場制作部のREADMEを優先する。

## 1. 素材を先に合成し、最後に光点へ変換する

狼だけを線・ベタ画像・HUDで画面に貼ると、光点でできた周囲から浮く。そこで、原画のRGBAを**地面や看板の素材色**へ合成し、その色を既存と同じ円形光点で描く。

流れは `原画 → world面とUV → 下地色への合成 → 投影・深度 → 円形光点`。スクリーンショットを背景として貼る方式ではない。文字・模様・壁面ロゴも同じ経路へ流せる。`ground-logo.mjs` / `surface-layers.mjs` / `stadium-mesh.mjs` / `scoreboard.mjs` が担当する。

芝生では `u = x / 幅 + 0.5`、`v = 0.5 - (z - 中心z) / 長さ` で素材を参照する。芝生外・壁際・ファウル側へは描かない。可視強度はRGBAのalphaと輝度から抽出し、暗い背景をそのまま持ち込まない。画像生成による透過加工は参照の厳密な画素切抜きではない。

明るさと発光は光点の素材合成に作用する。芝生ロゴ0.8倍は現在の採用値。壁面ロゴの明るさとは別設定である。発光を輪郭線の上書きで実現しない。

## 2. 狼の輪郭と最低限の周囲だけを細分する

全面を細かくすれば元の意匠と負荷が変わる。ロゴの外接矩形だけを細分しても、矩形の密度差が目立つ。このため可視マスクから近傍距離場を作り、輪郭の周りだけ芝生を含めて細分する。

`ground-logo.mjs` は幅192のマスクに余白を取り、前後2回の走査で近傍距離を近似する。厳密なEuclidean distance transformとは主張しない。`surface-layers.mjs` の `densityWeight()` は輪郭からの距離に余白を加え、移行幅の中を `1 - t²(3 - 2t)` で滑らかに減らす。矩形は走査範囲の絞り込みに使い、密度の最終形はマスクで決める。

採用初期値は細分6倍、余白0.6m、移行0.8m。UIでは2〜8倍を編集できる。細かいロゴと周囲の芝生を**同じ細分格子**で描くため、狼だけ別の線質にならない。物理計算の精度・判定頻度を変える設定ではない。

## 3. 遠近・面の傾き・遮蔽を共有する

すべての建築をworld座標に置き、カメラと同じ投影を通す。壁面のUVは遠近を考慮して補間する。投影された三角形を画面内の局所索引へ登録し、細分点の検索対象を減らす。元の地面・選手・屋根と共有する深度で、見えない面や光点を隠す。精密ロゴを最後に貼って選手や屋根を透過させない。

近くでは原画の細部を保持し、遠くや斜めでは画面上のsample範囲を大きくする。`texture-filter.mjs` はalphaを考慮したmipmapを一度作る。`material-lod.mjs` は投影サイズと傾きから密度とfilterの範囲を連続調整する。現在の深度によるfilter増分は最大15%。深度で明るさ・contrast・opacityを消さない。

当初の深度減光は遠景の狼が消えやすく本人が不採用とした。逆に固定の高密度・強い発光では遠くでも鮮明すぎた。現在は「存在感を保ち、少しだけぼやける」を優先する。係数は美術調整値であり、実測光学定数ではない。異方性sampleや露出統一などは将来比較可能。

## 4. 内野を固定し、球場固有の外周を編集する

`model.mjs` は内野・本塁・塁・線を固定したまま、外野距離・外周頂点・局所的な壁高・ファウル側の広さ・ウォーニングトラックを扱う。既存PNG・Coreを表示都合で変更しない。`renderer-patch.mjs` は凍結V114の描画scriptだけを変更し、元に完全逆変換できることとCoreのbyte一致をbuildで検査する。

新しい壁が絵に出ていることは、通常試合のHR・衝突・守備予測へ接続済みという意味ではない。この部門は表示の制作環境であり、正史の判定を画素や装飾から作らない。

## 5. 客席・外装・開閉式屋根を共通の立体として作る

`architecture.mjs` が設定、`stadium-mesh.mjs` が形状を担当する。外周は96区間を基本に分割し、5層の座席と階間の前面・通路、金の手すり、赤青の外壁、金のV形装飾、ガラス状の基壇、入口・階段をworld面と線で作る。

屋根は銀色の曲面葉、金トラス、青い縁。開閉率で葉を動かすが、開いた葉の幅は外形から制約し、外周を突き抜けないようにする。外観・内観・俯瞰・回転で同じ構造を確認する。円筒の点群を増やすだけでは参照の厚みや建築意匠を再現できなかったため、面の重なりと支持部を明示した。

## 6. 観客を個人actorではなく共有群衆タイルで表す

細かい個別観客の大量配置は密集した縞や過度な間引きに見えた。現在は `crowd-tiles.mjs` の小さな共有群衆素材を座席面に敷き詰め、座席区画のUVへsampleする。5層×4帯×96区間＝1,920区画。容量12万人と描画オブジェクト数を分離する。

LEDの実寸設定は0.07m。大きな線として描かず、群衆素材の短い光と抑えた発光として表す。赤青の色、発光、密度、身体サイズ、描き込み、満員/無観客を別々に編集できる。無観客や非占有部分では元の座席色を出し、黒く塗り潰さない。

本人の最終指定は**2コマの動作を2周、3コマの動作を1周**。現在の3姿勢の並びは `[0,2,0,2,0,1,2]`。1姿勢を2拍・2拍・3拍保持する意味ではない。`crowd.mjs` の時計は通常400msを基準に進み、観測済みの安打・HR等では短くする。公式結果をこの時計で決めない。イベントIDを重複消費せず、pause・hidden・reduced-motionを尊重する。

静止した設計室では最大3枚のscene画像を生成し、コマ送りは画像の切替にする。観客tickごとにworld全体を再構築しない。このcacheを通常試合へそのまま流用して、選手やボールまで静止させてはならない。

## 7. スコアボードも素材と立体の組合せにする

中央上部の狼と横長紺色LED、金の框・背面・側板・支持部、赤青の側部を共存させる。9回/RHE・BSO・球速をoffscreen Canvasへ描き、文字を素材としてmipmap/UV/局所光点/共有深度へ通す。スコアボードだけ画面へ文字を直貼りしない。

Rは各回の和。無効入力では直前有効表示を保ち、原因を入力部近くに出し、保存を止める。狼と表示盤のON/OFFは独立。表示盤OFFで確認カメラが飛ばないよう、照準点は立体構造側で保持する。小さい客席構成でも屋根内に収まる縮尺にする。現在の値は**設計用の表示見本**であり、公式試合のスコアではない。

## 8. 編集・保存・検証の契約

人間のUIとAI用API/CLIが同じmodelと検証を使う。無効値は確定させず、undo/redo、JSON入出力、明示保存で戻せる。旧JSONのoptional設定欠落はfallbackとして扱い、読み込みだけで項目を勝手に書き足さない。保存済みの利用者設定は新しいプリセットより優先する。

`BallparkStudio.inspect()` は設定だけでなくready、error、編集revisionと描画revision、ロゴの描画点、建築・群衆・投影などを観察できる。設定値が変わっただけでなく、描画revisionと画素も検査する。立体の遮蔽は別実装のray/triangleでも比較し、技術PASSを人間の美術承認へ昇格させない。
