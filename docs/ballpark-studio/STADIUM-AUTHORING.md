# 球場制作の作業指針と改善台帳

2026-10-25完成確認: 本人が現在の球場デザインを採用。芝生ロゴの初期明るさは0.8倍。最新の承認範囲・証跡・未接続境界は [CURRENT-accepted.md](CURRENT-accepted.md)。

2026-10-24。本人指定: 細部にロゴの素材技術を再利用すること、視点を変えても品質を維持する構造、制作上の判断を環境へ残すこと。ただし現方式を唯一の正解に固定せず、自己改善を認める。

この文書は次の担当が使う入口。最新の人間指示と実際の観察を優先する。実装方法/閾値は検証付きで変更できる。本人が明示した見た目・固定内野・通常試合との境界を、改善の名目で勝手に変更しない。

## 維持する目的 / 見直せる手段

| 維持する目的 | 現在の手段と改善の余地 |
|---|---|
| 既存の光点画面に素材を自然に馴染ませる | PNG+下地色→UV sample→局所光点。別の同等以上の素材処理も比較可能 |
| ロゴだけ線/画像で浮かせない | ロゴと周囲の下地を同じ格子にする。地面の輪郭距離maskと壁看板面の範囲は用途で使い分ける |
| 遠景が不自然に鮮明にならない | 投影面積/傾きによるLOD、mipmapと軽いぼけ。最新指示により深度でcontrast/opacityを落とさない。係数は暫定 |
| 視点を変えても同じ球場に見える | 外装/階層/屋根/看板を共通world座標に置き、同じ投影と深度で描く。形状の分割方法は改善可 |
| 内野と野球の仕様を壊さない | 塁/白線/本塁/PNG/Coreは固定。表示の細分を判定精度へ混入させない |
| 観客の量とLED表現を両立させる | 共有群衆タイルと3コマ、満員/無観客の独立状態。1人ずつの巨大actor展開を避ける |
| 設定変更を戻せる | 入力検証、直前有効値保持、undo/redo、JSON/明示保存。旧JSONのoptional欠落は無追記 |
| 長期間の保守と軽さ | 小さな局所領域だけ精密化し、素材の前処理は一度、静止設計室は最大3画像cache。実測して採否を決める |

## 実装入口

- `tools/ballpark-studio/stadium-mesh.mjs`: 建築の世界座標、面のmaterial/UV、透視補正、遮蔽、局所密度。
- `ground-logo.mjs`: 採用PNG/可視マスク。`sampleGroundLogo()` は承認済み芝生。`sampleLogoUV()` は壁面等への共用入口。
- `texture-filter.mjs`: 透明度を考慮した縮小画像の階層を一度生成し、画面上の1点が覆う範囲に応じてsample。縮小画像をHUDとして貼らない。
- `material-lod.mjs`: 投影サイズ/傾きから密度上限とsample範囲を連続計算し、深度の影響は軽いfilter増分に限定する。inspectの `architectureRender.detail.logoProfiles` で確認可能。
- `surface-layers.mjs` / `renderer-patch.mjs`: 素材合成→共通circle dot→共有world depth。選手や屋根を透過する専用overlayを作らない。
- `preview-bridge.js`: 8カメラと回転。見やすいカメラと形状の正しさは分けて検証する。
- `crowd-tiles.mjs` / `crowd.mjs` / `studio.mjs`: 群衆素材、動作時計、設計室cache/編集/保存。

素材拡張時は、原画/出典を保存→配置する面とUVを決める→下地へ合成→投影サイズに応じたsample→局所の光点→共有深度、の順に追加する。装飾の模様も素材色として計算できる。大きな面を不用意に細分せず、必要な領域だけにする。

## 作業ループ

1. 対象の専用CURRENTと最新の人間指示を読み、承認済み/未承認/未実装を区別する。造形の好評を未接続の試合機能への承認に転用しない。
2. 参照画像と現在の同じ視点を比較し、構造・投影・遮蔽・素材sample・密度・照明のどれが原因か分ける。遠近の違和感を即座にカメラ不具合と決めつけない。
3. 変更前HTML/設定/hashを保存。変更対象・理由・代案・検証/復旧を専用docsへ残し、小さい差分で実装する。
4. `build.mjs <新label>` と `verify-source.mjs <同label>` で凍結V114/Core/入力/成果物を確認。過去evidenceを上書きしない。
5. unitに加え、8視点・近/遠・斜め・回転・屋根開閉・満員/空席・保存/取消・320/390幅を実Chromeで確認。精密点は独立ray/triangleでも遮蔽を検査する。
6. 画素一致を守る領域と意図して変える領域を明記する。建築変更を旧全景へ戻してテストを通したり、物理を変えて絵を合わせたりしない。
7. 必ず画像を見て判断する。テストPASSでも見た目が悪ければ再検討し、候補を採らなかった理由も残す。性能計測と造形評価は別に記録する。
8. 変更内容/未検証/原FAIL/次手順を専用CURRENTへcheckpoint。GitHubの既存判断記録へ公開可能な要点だけ集約。私的本文/生ログ/credentialsを投稿しない。

## 暫定値と未解決点

- 壁面ロゴLODの80px基準（600×432のrenderer論理画面上の短辺）、70〜420のcamera-depth区間は暫定。前段の深度によるcontrast/発光の減少は本人が過剰と判断し撤回。現在は減光せず、filter footprintの増分を最大15%とする。実測の光学定数ではない。
- 現filterは等方的なmipmap。非常に斜めの面ではぼかし過ぎる可能性があり、異方性sampleを比較する余地がある。
- ロゴの強調だけを調整している。球場全体で光源/材質/露出を統一すべきかは、参照と複数視点の比較を踏まえて別途判断する。物理的に誤った一律の距離二乗減光を面全体へ適用しない。
- 高密度と細部保持を最大化すれば常に良いわけではない。低解像度の意匠に合う情報量、ちらつき、可読性、生成時間を比較する。
- 自由回転の全角度、極端な全設定組合せ、実機スマホ/Safari/長時間性能は全保証していない。検証範囲を正直に残す。
- 設計室の静止scene cacheを通常試合へそのまま流用し、選手/球を止めない。新球場の通常試合への衝突/守備/HR/イベント連動は依然別工程。

改善は「困っている見え方→原因の証拠→候補比較→採否理由→再現可能な検証」の単位で残す。新方式が良ければ現方式を更新してよい。古い根拠/失敗は消さず、現行と履歴を区別する。

## 描画負荷の確認

素材の前処理は読み込み時だけ行う。現在の壁面mip画像は追加2,102,544 bytes、静止設計室の3画像cacheはRGBAで12,441,600 bytesが目安（他のscene/PNG展開は別）。設定変更後の生成時間、観客コマ送り中のworld再構築回数、細分point数、初期化の待ち時間を分けて測る。これらの予算/方式も固定の正解ではなく、端末の実測と見た目で見直してよい。
