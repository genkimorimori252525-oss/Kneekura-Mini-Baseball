## 3. 基本構造と検出されたボトルネック

1. 単体HTMLは約32MB。OpenBiomechanics実測軌道由来の大型JSONが約29.6MBで**673クリップ**。旧起動処理は全量を解析・複製・検証・凍結するため、起動待ちと大量のJSオブジェクトを生んでいた。
2. `#field` の通常バッファは `1200×864`。地面を約1.6万箇所の4pxドットで投影し、動くカメラでは視点・三角関数・地表判定・深度などを繰り返し計算していた。
3. 球場を毎回描画し、選手名DOM、スコア表、履歴・配球図なども同一状態で再構築する箇所があった。
4. 旧版には独立v23のローカル試合実装と、後の `v33-offline-core-match` 風の正式Core観測レイヤーが共存する。**どの実行経路かを区別し、旧v23側の時間軸まで変更したとは書かない**。

## 4. 実装した軽量化（時系列）

### v1: 高FPS・再計算削減・静的キャッシュ

- `v33-offline-core-match` の通常描画間隔を **55ms → 約18.333ms（3倍）**、投球に関する高頻度の表示サンプリングを **22ms → 約7.333ms（3倍）**。旧試作の比率（通常:投球 = 55:22、投球側は約2.5倍）を保持。`requestAnimationFrame` を使うため、この数値は**実画面FPSや端末Hzの保証ではない**。正史時計・シミュレーションtick・結果判定は不変更。
- `KneekuraMeasuredBatLibrary` の通常利用は既定12クリップに限定してオブジェクト化。既定にない `physical.clipId` が指定された時は全673件を復元可能なフォールバック。**v1では大型の全文JSON.parseが残っていた**。
- 地面の既存Canvas円ドットを一度8×8ピクセルのスタンプにし、再使用可能な `ImageData` にコピー。元の位置・色・透明度・描画順・4px格子は変えない。
- `paintPark` で投影条件が本当に同一の捕手・俯瞰などに限定した背景キャッシュ。カメラ追尾時は再描画。動的な選手・ボール・バットはキャッシュで止めない。深度や地面マーキング情報も描画に整合させる。
- 選手名とテキスト計測、スコア・履歴・配球図等の同一状態でのDOM再生成を省く。tickのフレーム検索を二分探索へ変更。

### v2: 動くカメラの地面処理と起動負荷を追加削減

- 12クリップの**厳密な原本サブセット**を別の埋め込みJSONとして同梱し、通常起動ではそこだけ `decode` /検証する。元の673クリップ原本JSONは変更せず保持し、非既定クリップを指定した時に初めて全件を復元。結果、HTMLサイズは約0.62MB増える。**高速化はメモリ展開・起動CPUの削減で、ファイル転送サイズの縮小ではない**。
- 旧実装の `groundAt` / `project` / `surfaceAt` / `ground` のうち、同一カメラフレームに共通の三角関数を1度計算し、同じ地面サンプル行で不変な射線成分・交差深度を再利用。座標・地表色・遮蔽に必要な判定は引き続き行う。
- `groundPixels32` と再利用スタンプを使い、同一RGBAの4チャネルを32-bit単位で転記。地面座標キーは `x*512+y` の一意な数値キーを利用して文字列連結を避け、最終画面に不要な地面アンカー配列を削減。
- 円形フェンスの**確実に内側**と判定できる場所だけ境界の高コスト関数を省略。境界付近は旧式の厳密な判定を維持。
- `putImageData` による最終地面ラスター転送は残っている。これが今後の調査候補。

**注意:** 旧v33の「投球ボール補助レイヤーの高頻度更新」という仕組みを、最新版の正史映像設計へそのまま移植してはならない。2026-10-16以降の正規方針は**球単独でなく、全アクターが同じCanonical時刻を観測するシーン全体の状況適応描画**。残すのは「低動作場面と高動作場面の相対的な描画密度を保ちながらベースを引き上げる」意図であり、古い実装方式の踏襲義務ではない。

## 5. 実測（混同禁止）

### v1 vs 原本：実再生

PC上のChromium/Playwrightを幅390 CSS px・DPR 2で試した**仮想モバイル条件**。AndroidやiOSの実機測定ではない。

| 測定場面 | 原本 | v1 |
| --- | ---: | ---: |
| 投球前の区間・実再生FPSの一例 | 約17.0fps | 約53.6fps |
| 投球を含む区間・実再生FPSの一例 | 約16.6fps | 約39.3fps |

同seed2球、捕手/俯瞰/投手/打者などの10場面で画素・ラベル・スコア・判定等 **180項目が一致**。`node --check` で対象の実行可能な16 inline JSブロックに構文エラーなし。旧HTMLとv1の完全な9回一致は**未検証**。

### v2 vs v1：地面の処理時間中央値

同じChromium環境で各10フレーム。これは**地面描画のみ**であり全体のFPSではない。

| カメラ | v1 | v2 | 短縮率 |
| --- | ---: | ---: | ---: |
| 打者 | 12.05ms | 4.20ms | 約65% |
| 投手 | 10.35ms | 3.10ms | 約70% |
| 走者 | 8.35ms | 3.20ms | 約62% |

別の単回測定（v1→v2）で初期化時間 **8,506ms→5,936ms**、手動GC後の `performance.memory.usedJSHeapSize` **112,263,579→82,710,905 bytes**。実メモリ総量でも統計的な代表値でもない。熱・キャッシュ・機種によって変わる。

### v2 の一致検証

- 幅390px / DPR2：5視点×5時点=**25状態**、球場・白球・バット・配球図の**計100 Canvas画像の全画素ハッシュが一致**。状態・選手名も差異なし。
- 幅1050px：2seed×5視点×3時点=**30状態**、球場Canvasの全画素ハッシュ・表示状態が一致。
- 2seedで生成した**初回投球**のCore記録チェックサムが一致。例の結果分類は `live_ball` と `fly_out`。これは全試合の物理・審判・公式記録の完全証明ではない。
- オンデマンド復元で673クリップを回収。非既定 `obp-111_1` の137サンプルを取り出した。実行時エラーなし。
- 旧版→v1 / v1→v2の各段階に比較結果があり、**v2で実機60fpsを確認した記録ではない**。

## 6. 棄却・失敗した候補も残す

- 地面ドットを**巨大な1つのCanvasパスに一括結合**する案は、計測でむしろ遅くなり画素差も生じたため**採用せず元に戻した**。同じ「まとめる」でも、画素が変わらない再利用スタンプの方が有効だった。
- 画質低下、PNG差替え、地形の近似式への改変、音・演出削除、公式結果や球物理の近似、高FPSのために未確認のボール独立補間などは**実装していない**。
