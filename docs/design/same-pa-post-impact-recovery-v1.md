# 接触後の連続制御と実行

2026-10-17。承認済みのCore・Host統合計画のうち、実接触から次の物理境界へ進む部分。OpenBiomechanicsを参照し、UIと通常HTMLは変更しない。

## 元の反動から開始する

`PostImpactBatBodyControlV1`は、元の結合World queryを再計算し、最初の実接触から開始する。呼出側の接触時刻・インパルス・姿勢の注入は受け付けない。並進・角速度は実際の剛体衝突結果を使い、grip速度は重心速度から剛体の回転成分を差し引いて求める。位置・腰・保持手は接触時の値を保持する。

終点は元の実測参照の有限な終点姿勢であり、そこで静止する明示的な回復制御を作る。gripと腰は三次Hermite、姿勢は正規化した四元数三次曲線とし、反動後の速度から連続させる。元のスイングを接触後もそのまま実行したり、即時に速度をゼロへ置き換えたりはしない。

手とグローブの到達距離、胴体と保持手の間隔、足の制御、地面・他の身体形状・バットとの間隔、バット・身体の速度上限を連続区間で証明する。制御期限の更新は行わず、元の各期限を超える要求は拒否する。

これは有限な運動学的モデルである。筋トルク、力の釣り合い、実測の神経反応時間を校正したとは扱わない。

## 球も同じ時刻から継続する

`PostImpactBatBodyWorldV1`は、元のoriginTickと正確な小数の接触時刻を保つ。衝突による新しい球速・スピンでSource積分を開始し、材質の回転位相も前の投球から継承する。丸めたevent tickを新しい物理基点にはしない。

バットは半径profileの各区間を正確な凸形状として扱う。元の接触探索のbracketと丸め誤差境界を再読し、分離速度と曲線の加速度境界から、接触直後の分離を証明する。実際に離れた数値witnessも要求する。球を押し出したり、バットを一定時間だけ衝突対象から外したりはしない。

元の49個のother-actor形状から打者の胴体・保持手の2個だけを実制御へ置換し、残る47個と、別制御の投手の手も残す。つまり元の投手手球を含む50身体形状と実バットを扱う。地面または別の最初の接触があればそこで停止し、制御終点へ到達したことにはしない。

## 消耗後の能力と実行権

`InitialJointRecoveryCommand`は、実行済みprefixの消耗view、元の人物hash、投影状態hash、明示的なSI能力応答の校正を結ぶ。疲労0〜1を覆うSI sampleから上限を補間し、元の受理済み上限を超える値を拒否する。相対能力値やリーグ係数は使わない。

今回のNative試験では、疲労0でsweet spot50m/s・身体5m/s、疲労1で40m/s・4m/sという明示的な合成校正を使う。打者の投影疲労0.075に対し、49.25m/s・4.925m/sで回復曲線を照合した。これは上限による実行可能性の確認であり、既存の打撃を後から遅くしたり、NLB本人の実測能力を証明したりする処理ではない。

V1で受理する回復モデルは`EXPLICIT_SYNTHETIC_IMPACT_RECOVERY_V1`、反応仮定は`ZERO_DELAY_KINEMATIC_TEST_MODEL`である。実測の神経・筋肉モデルとして製品へ昇格しない。実測根拠のある応答への接続は未完了として残す。

`SqliteInitialJointRecoveryExecutionStore`では、受理された有限commandを一回だけ使う実行権とし、親の実行・消耗viewを同じtransactionで一意に消費する。新tableは`pa_joint_recovery_v1_executions`で、元の77tableを変更しない。現在のofficial frame・予約状態・観測判断head・Worldを再認証し、保存後も通常ownerで再計算する。

新しく動いた区間には新しい累計消耗評価が必要であり、前のTOTALをそのまま使って次の動作へ進まない。`requiresCumulativeWorkloadReassessment:true`、`nextMotionAllowed:false`を残す。

## 検証と次の接続

Nativeの実接触0.46910977857333824秒から、0.546911秒・tick11134216へ、約78msの実時間を進める。条件付き計算の生成物は`verification-authored-with-bat-post-impact-v1`、採用試験は`verification-authored-with-bat-recovery-v1`。採用・再読の成立は各reportとmachine receiptで確認する。

後続がある状態で親の実行や消耗viewを削除すると、元ownerは再生成を拒否する。索引を移動し、最後のduplicate JSON keyで参照を隠した場合もraw typed referenceを調べる。検証で削除・改ざんした行は元へ戻し、全行・schemaの復元を確認する。

初期の有限差分テストの誤差見積もり、readonly型へ代入したテスト、地面で止まる正しい結果をmovingと決めつけたテストはFAILを保全して修正した。最初のcold readerはJSONで表せない`-0`と`0`の違いだけで失敗した。物理は変更せず、全値が有限なinert dataであることを検証したうえで、ownerと同じcanonical JSONを比較する。
