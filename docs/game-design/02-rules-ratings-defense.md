# NPB規則・能力査定・守備シミュレーション設計

更新日: 2026-09-17
状態: 実装前の仕様。年度規則の原文照合とテストを前提とする。

## 1. 規則プロファイル

初期プロファイルは `NPB 2026` とする。試合進行コードに年度固有の条件分岐を散在させず、以下のようにルールと運用をプロファイル化する。

```ts
type RuleProfile = {
  id: "npb-2026";
  ballsForWalk: 4;
  strikesForStrikeout: 3;
  outsPerHalfInning: 3;
  designatedHitter: boolean;
  extraInningPolicy: ExtraInningPolicy;
  substitutionPolicy: SubstitutionPolicy;
  scoringPolicy: ScoringPolicy;
};
```

`NPB 2026` の詳細な大会運用は公式規則・当該大会要項と照合し、プロファイルに記録する。レギュラーシーズン、ポストシーズン、二軍、特別試合で異なる要素を、物理モデルに混ぜない。

## 2. 最初に固定する野球規則

以下は見た目より先に、入力状態・出力状態・回帰テストを持つ。

| ID | 規則／状況 | 必要な判定 |
| --- | --- | --- |
| R-01 | 4ボール、3ストライク、3アウト | 打席と半回の遷移 |
| R-02 | ファウル | 二ストライク後の通常ファウルは三振にしない。バントのファウルは別扱い |
| R-03 | ファウル飛球 | 捕球可能で捕球された飛球はアウト。地面に落ちたファウルと混同しない |
| R-04 | フォース | 走者と打者走者の到達義務を塁の占有から再計算する |
| R-05 | タッグ | フォースが消えた後は走者へのタグを要する |
| R-06 | 第三アウトと得点 | 打者走者の一塁前アウト、またはフォースアウトが第三アウトなら、そのプレーの得点は認めない。時間差アウトも扱う |
| R-07 | タッグアップ | 捕球成立後に離塁可能。早い離塁はアピール対象として状態を残す |
| R-08 | インフィールドフライ | 適用条件、宣告後の打者アウト、落球時の走者状態を分離する |
| R-09 | 死球・暴投・捕逸・ボーク | 投球結果、走者進塁、責任記録を分ける |
| R-10 | 併殺・三重殺 | アウトの順番ごとにフォースと得点可否を評価する |
| R-11 | 犠打・犠飛 | 打者記録、アウト、走者進塁を同じプレーから確定する |
| R-12 | 失策・野選・安打 | 記録員判断の層と物理結果の層を分ける |
| R-13 | 代打・守備交代・投手交代 | 打順、守備位置、投手資格の整合性を守る |

特に `R-06` は優先度 P1 である。二死満塁の内野ゴロで一塁が第三アウトになった場合、三塁走者が先にホームを踏んだように見えても得点は入らない。このケースは既存候補エンジンの調査で不整合が確認されており、移植前にテストで封じる。

## 3. 正史状態とプレー時系列

Mini Baseball は結果を先に抽選して映像を後付けするゲームにはしない。内部では一球ずつ投球を解決し、コンタクト後は打球、守備9人、走者、送球を同じ正史時間軸で進める。

```text
ScoutingEstimate + GameContext
  → DefensiveAlignment

PitchIntent / BatterIntent
  → PitchWorldState(t)
  → PitchResult
  → ContactResult または PlateAppearanceResult
  → BattedBallPath
  → DefenderWorldState[9] + BaserunnerWorldState[]
  → FieldingIntent / CoverageIntent / ThrowIntent
  → TimedMatchEvent[]
  → RuleEngine が得点・アウト・記録を確定
```

- `PitchWorldState` は投球ごとの球速、軌道、位置、時間を持ち、ボールカウントだけを結果として抽選しない。
- `BattedBallPath` は位置・速度・回転・地面／壁との衝突を持つ。
- 守備側9人はそれぞれワールド位置、速度、移動目標、現在の役割を持つ。
- `TimedMatchEvent` は野手の到達、捕球、処理、送球、塁到達、タグ、得点を時刻順に持つ。
- 規則判定はイベント順で行う。表示やカメラはこの出力を読むだけである。
- 乱数は試合シード、打席シード、必要に応じてプレーシードを保存して再現可能にする。

### 3.1 シミュレーション時間

Core は描画FPSから独立した固定のシミュレーション時間軸を持つ。具体的な刻み幅は、捕球・送球・塁到達の順序を安定して再現できる精度と、軽量に大量試合を回せる性能の両方を測って決定する。

```text
Simulation Clock
  → CanonicalWorldSnapshot(t)
  → CanonicalWorldSnapshot(t + dt)
  → ...

Render Clock
  → Snapshot を読むだけ
```

表示側は前後の正史スナップショットを補間してよいが、補間結果を RuleEngine へ戻さない。30fps、60fps、描画OFF、高速進行で同じ入力・同じシードなら、正史イベント列と最終状態は一致しなければならない。

## 4. 公開査定と隠し査定

### 4.1 公開する能力

プレイヤーが直感的に比較できる情報は少数にする。

| 区分 | 公開能力の例 |
| --- | --- |
| 打撃 | ミート、パワー、選球眼、バント |
| 走塁 | 走力、盗塁、走塁 |
| 守備 | 守備力、肩力、守備位置適性 |
| 投球 | 球速、制球、変化、スタミナ、球種 |

公開値は能力の完全な説明ではない。例えば「守備力」が同じでも、初動、打球判断、送球の正確さまで同じにしない。

この表は「プレイヤーへ公開できる情報」の例であり、すべてを同じG〜S Headline Ratingとして同時表示する意味ではない。例えば盗塁・走塁等はA〜G Graded Trait Familyを主要Projectionとして使える。バント等でRatingとTraitの両方を表示する場合も、同じsource of truthを別能力として二重入力しない。

また、公開値はすべて同じ尺度とは限らない。

- ミート、パワー、守備力、制球等はリーグ文脈を持つPresentation Projection候補
- 球速、走力、肩力、スタミナ等は物理量・身体性能へ接続するABSOLUTE_PHYSICAL候補
- 守備位置適性、先発 / 中継ぎ / 抑え適性は本人と役割の適合性を表すSUITABILITY
- 球種、投打左右、年齢、身長等は事実・属性

一軍 / 二軍、守備位置、投手役割は原則として一覧・ランキングの絞り込み条件であり、同一リーグ内の公開能力尺度そのものを別物にしない。

UI用の0〜100、G〜S、Trait、図は正史能力を説明するProjectionであり、それ自体をMatch Coreへの入力へ戻さない。

### 4.2 隠し査定

隠し査定は結果を不透明にするためではなく、実在するプレー差を表現するために導入する。初期候補は以下である。

| 区分 | 隠し能力 | 効果の例 |
| --- | --- | --- |
| 打撃 | ゾーン認識、スイング判断、芯に当てる精度、方向適性、打球角度傾向 | 見逃し、空振り、打球方向、強い打球 |
| 投球 | リリース再現性、球種別の変化品質、打者からの見えにくさ、クイック、走者警戒 | 四球、球質、盗塁阻止、疲労時の崩れ |
| 守備 | 守備位置別適性、初動、打球判断、追い方、捕球、送球移行、肩の強さ、送球精度、タッグ | 捕球地点、失策、併殺速度、送球逸れ |
| 捕手 | 捕逸抑止、ブロッキング、送球移行、送球精度、配球理解 | ワンバウンド、盗塁、投手との相性 |
| 走塁 | リード、スタート、打球判断、進塁判断、帰塁、スライディング、走路変更 | 盗塁、次塁判断、タッグアップ、挟殺 |
| 身体耐久 | WorkCapacity / Stamina、FatigueResistance、RecoveryCapacity | 一登板の持続、疲れにくさ、登板後の回復。絶対身体能力として保持 |
| 状態 | CurrentFatigue、Condition、ActiveEmotion等 | 現在の疲労・当日の発揮状態・心理状態。原因を二重計上しない |
| 学習 | 対戦Exposure / Familiarity | 認識、予測、調整速度。リーグ名ではなく実際の経験から蓄積 |
| 監督 | 傾向推定、情報更新、サンプル評価、対戦条件の解釈、配置比較 | 守備シフトの予測精度と配置選択 |

心理状態や読み合いはこの状態層に属する。内部感情値・心理ゲージ・監督が内部で持つ打球方向確率は直接表示しない。ただし `05-psychology-emotion.md` で定義する `ActiveEmotion` が成立した場合の単一感情マークは、実際の挙動変化を知らせる明示的な例外とする。

### 4.3 査定を増やす条件

新しい査定項目は、次を満たす場合のみ導入する。

1. 現実の野球で、既存能力と独立して説明できるプレー差がある。
2. データまたは専門的な根拠により、能力の方向性を評価できる。
3. 同じ入力シードの比較試合で、意図した結果差を確認できる。
4. 公開値との二重計上や、乱数による見かけの差を避けられる。

査定は一度に固定しない。各実装段階で、必要になった能力を追加し、既存データとの相関を確認する。

### 4.4 公開査定・TraitのPresentation Invariance

公開査定やTrait表示は、試合結果の原因ではない。

同一true player state、同一Match input、同一seedについて、以下だけを変更してもCanonical Eventsと最終結果が一致しなければならない。

- 0〜100換算式
- G〜S境界
- Traitの表示名・色
- UI上の変化量量子化
- ランキング母集団・表示フィルタ
- 説明文・表示順

また、守備位置適性や投手役割適性は走力・肩力・スタミナ等の汎用身体能力を再加算する値にしない。役割固有の習熟・判断・ルーティンを主に表し、同じ弱点を二重に補正しない。

## 5. 守備AIの設計

守備AIは、打球発生後だけを扱うものではない。`試合前・打席前の読み → 初期配置 → 打球への反応 → 9人の役割分担 → 捕球・送球・タグ` を一つの系として扱う。

### 5.1 共通の目的関数

守備の目的は全チーム共通で、現在のゲーム状態からの期待勝率を最大化することである。残りアウト、得点差、走者、回、ホーム／ビジター、延長、同点・逆転・サヨナラ条件をすべて入力に含める。

```text
優先順位
1. このプレーで直ちに敗戦・サヨナラ負けを招く失点を防ぐ
2. 同点・逆転・勝敗に直接影響する失点を防ぐ
3. アウトを取る、追加進塁を止める、失策を避ける
4. 次のプレーに不利な走者配置を残さない
```

攻撃的なチームという設定であっても、この優先順位を崩さない。選手能力は「どの選択が実行可能か」と「どれほど正確に実行できるか」に影響し、敗戦条件を無視する性格付けには使わない。

### 5.2 監督・スカウティングによる打席前配置

打者の真の傾向と、守備側が知っている傾向を分離する。

```ts
type ScoutingEstimate = {
  directionDistribution: DirectionDistribution;
  trajectoryDistribution: TrajectoryDistribution;
  contextAdjustments: ContextEstimate[];
  uncertainty: number;
  sampleAge: number;
};
```

- 打者自身のモデルには、球種・コース・投手左右・カウントなどに応じた真の打球傾向が存在し得る。
- 守備側監督は真の傾向を直接参照せず、過去に観測できた打球、スカウティング、当日の打席、投手との相性などから `ScoutingEstimate` を得る。
- 推定には必ず不確実性を持たせる。初対戦、最近フォームを変えた打者、少数サンプルでは確信を弱める。
- 監督能力は、推定誤差、最近の情報への追従、少数サンプルの扱い、対戦条件の解釈、候補配置の比較へ反映する。
- 「名監督なのでシフト成功率 +20%」のような直接補正は禁止する。監督は未来の打球を知るのではなく、より良い推定を作りやすいだけである。

監督は推定分布と局面を使って複数の `DefensiveAlignment` を比較する。

```ts
type DefensiveAlignment = {
  defenders: ReadonlyArray<{
    playerId: string;
    registeredPosition: DefensivePosition;
    start: Vec2;
    primaryResponsibility?: CoverageResponsibility;
  }>;
};
```

`registeredPosition` はルール・適性上の守備位置であり、`start` は現在のフィールド座標である。この二つを分離する。

### 5.3 任意座標を許す連続空間の守備

守備位置ごとの固定座標を前提にしない。規則上合法なら、センターを二遊間の間へ置くような極端なシフトでも同じワールドモデルで処理する。

```ts
type DefenderWorldState = {
  playerId: string;
  registeredPosition: DefensivePosition;
  position: Vec2;
  velocity: Vec2;
  intent: DefensiveIntent;
  assignment: DefensiveAssignment;
};
```

- `registeredPosition` が CF でも、`position` は内野に置ける。
- 捕手・投手を含む9人全員を `DefenderWorldState` として持つ。
- 打球後に「関係する2〜3人だけ」を動かさない。9人全員が、処理、塁カバー、中継、バックアップ、後逸対応、次走者への備えのいずれかへ動く。
- 誰もボールに触らない場合でも、その選手の移動には意味がある。Natural Baseball ではその移動がそのまま描画される。
- 極端なシフトで通常の守備位置が空けば、他の野手がその空間をどこまで補完するかも守備計画の対象にする。

### 5.4 打球後の9人守備と役割分担

```text
打球発生
  → 9人全員の現在位置・速度から到達可能時刻を予測
  → 捕球／処理候補を比較
  → 主処理野手を選ぶ
  → 残り8人へ塁カバー・中継・バックアップ・後方カバーを割り当てる
  → 走者ごとの到達予定とフォース状態を予測
  → 送球候補を期待損失で比較
  → 移動・捕球・送球・タグ・進塁を時刻順に確定
```

野手の役割は固定ではない。最短到達する野手が一塁手の場合、投手や二塁手が一塁カバーに回る必要がある。外野返球では、中継とバックアップを配置する。センターが内野シフトに入っているなら、左右の外野手などが通常より広い後方範囲を受け持つ可能性がある。

役割は最低限、次を別々に持つ。

- `ballHandler`: 打球を直接処理する
- `baseCover`: 塁をカバーする
- `relay`: 中継点へ入る
- `backup`: 送球・捕球の後逸に備える
- `deepCoverage`: 空いた後方・長打域を補完する
- `hold / observe`: 局面上、無理に移動しない方が良い場合

一人へ競合する役割を同時に割り当てない。打球の進行、送球、走者判断が変われば、決定論を壊さない定義済みの再計画点で役割を更新できるようにする。

### 5.5 評価する候補

各守備案は、最低限次を比較する。

- 捕球または止める確率とその時刻
- 現在位置から捕球点までの加速、方向転換、到達可能性
- 捕球後の持ち替え、送球の到達時刻、送球逸れ、受け手の捕球・タッグ成功率
- 各走者が次塁・本塁に到達する確率
- フォースアウトかタッグか、第三アウトか
- 失点・同点・逆転・サヨナラに対する重み
- 他野手の塁カバー、中継、後逸バックアップの成立可否
- その守備案によって次の送球・進塁へ残るリスク

概念的な評価式は以下とする。実装初期は期待勝率の近似テーブルを用いてよいが、最終的に局面を無視した固定優先順位には戻さない。

```text
score(plan) =
  - P(即時敗戦失点) * 非常に大きい重み
  - P(同点・逆転失点) * 状況重み
  + P(アウト) * 状況重み
  - E(追加進塁・失策・後逸)
  - E(カバー不在による二次被害)
```

### 5.6 守備シフトと打者成績の関係

守備シフトは打者の能力値や安打率を直接変更しない。

```text
同じ打者
同じ投手
同じスイング
同じコンタクト
同じ打球軌道
        ↓
異なる DefensiveAlignment
        ↓
異なる野手到達時間・捕球・送球
        ↓
結果として安打／アウト／進塁が変化
```

この差の累積として、BABIP、安打、長打、得点などの成績が変わる。シフトの効果を検証するときは、同一の打球集合を複数配置へ流して比較する。

監督の読みが当たった場合でも、野手が遅い、捕球を失敗する、送球が乱れることはある。反対にシフトの読みが外れても、選手の範囲や判断で救うことがある。この二つを混ぜない。

また、同じ `DefensiveAlignment` まで確定した後は、監督能力を理由に打球を野手へ寄せたり、守備選手の速度を上げたりしない。これにより「監督の読み」と「選手の実行」を別々に評価できる。

### 5.7 既存候補エンジンからの改善点

先行調査したエンジンには、捕球可能な野手を到達時間だけで選び、送球先を固定優先度で選ぶ部分がある。移植時には以下を置換する。

| 現状の単純化 | 必要な置換 |
| --- | --- |
| 守備位置により固定した野手配列 | 登録守備位置とワールド座標を分離し、任意配置を許す |
| 打球に関係する野手だけを処理 | 守備側9人全員を連続空間で更新 |
| 最短到達野手だけを選択 | 捕球確率、処理、カバーへの影響、局面価値まで比較 |
| 固定の塁カバー | ボール処理役と現在位置に応じた動的カバー |
| 固定の中継・バックアップ | 打球、走者、配置に応じて毎プレー割り当て |
| 送球先の固定優先度 | 走者の到達予定と勝敗条件に基づく期待損失最小化 |
| 受け手が固定座標 | 受け手の移動、捕球、タグ時刻を含む |
| 一律の走者進塁 | 走者ごとのリード・判断・走力・打球認識で決定 |
| シフト効果を直接確率補正 | 配置による到達時間差から結果を自然発生させる |
| 監督が打者傾向の真値を参照 | 観測データから作る推定分布と不確実性を使う |

## 6. 球場と物理

球場は `StadiumProfile` として定義する。

```ts
type StadiumProfile = {
  outfieldFence: FenceSegment[];
  foulTerritory: Polygon;
  wallHeightAt: (point: Vec2) => number;
  surface: SurfaceProfile;
  wind: WindProfile;
};
```

球場の大きさや風は、打球の着地、跳ね方、壁への到達、野手の追いつける範囲に影響する。速報 UI の情報量には含めない。点描の球場は `StadiumProfile` と正史ワールド座標を描くだけであり、別の当たり判定を持たない。

## 7. 必須テストケース

| 分類 | ケース |
| --- | --- |
| 規則 | 二死満塁、内野ゴロ一塁アウトで得点なし |
| 規則 | 一死満塁、ゴロ併殺で得点なし／時間差を判定 |
| 規則 | ファウル飛球を捕球してアウト |
| 規則 | 二ストライク後の通常ファウルと、バントファウルの差 |
| 規則 | インフィールドフライで走者にフォースなし |
| 投球 | 一打席命令のまま内部では一球ごとの球種・コース・結果を再現する |
| 守備 | 一塁手が処理するゴロで投手が一塁をカバー |
| 守備 | 外野返球で中継・本塁バックアップを配置 |
| 守備 | 打球後、直接処理しない野手を含む9人全員に妥当な役割または待機判断がある |
| 守備 | 中堅手を二遊間付近へ置いた配置でも、捕球・カバー・後方補完が破綻しない |
| 守備 | 同点最終回の三塁走者を、より簡単なアウトより優先して止める |
| シフト | 同じ打球を通常守備と特殊シフトへ流し、位置差から安打／アウトが変化する |
| シフト | 同じ配置が確定した後は、監督能力だけを変えて打球・野手速度・捕球結果を直接補正しない |
| 監督 | 打者の真の傾向と監督の推定傾向を別状態として保持し、読み違いを再現できる |
| 走塁 | 捕球前離塁、正しいタッグアップ、アピール可能状態 |
| 再現性 | 同一シード・同一入力で全イベントと最終状態が一致 |
| 再現性 | 30fps、60fps、描画OFFで正史イベントと最終状態が一致 |
| 統計 | 同一打球集合を複数の守備配置で処理し、成績差を物理・配置差まで追跡できる |
| Presentation | UI査定式、G〜S境界、Trait色・名称だけを変えても同一seedのCanonical Eventsが完全一致する |

テストを満たさない「それらしく見える」アニメーションは完成とみなさない。逆に、Core が計算した動きを正しく描いた結果として見た目が不自然なら、表示を捏造するのではなく、Core の計算・査定・判断を修正する。
