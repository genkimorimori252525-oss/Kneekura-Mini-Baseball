# 試合体験・監督モード・表示設計

更新日: 2026-09-17
状態: 実装前の体験仕様

## 1. 目指す体験

軽量な自動試合であっても、配球・打撃方針・走者・守備が一つの結果につながる感覚を作る。プレイヤーが見るのは「確率の数値」ではなく、速報画面と、打球後の俯瞰アニメーションである。裏では同一の試合状態が連続して進み、画面はその一断面を描画する。

### 進行の単位

```text
前打席の確定結果
  → ラインアップ／走者／スコアを更新
  → 次打席の攻守が各一つの方針を選ぶ
  → 打席中はエンジンが投球を連続解決
  → 打球なら物理・守備・走塁を同じ時系列で解決
  → 次の打席へ
```

ここでの「次打席の方針」は、一球だけへの入力ではない。例えば「内角中心」は当該打席の配球傾向を変え、「送りバント」は当該打席の打者・走者の行動傾向を変える。ボールカウント中にプレイヤーへ何度も確認を出さない。

## 2. 画面の役割

### 2.1 打席中

- 打撃側を指揮するときは、打者から投手を見る視点を主にする。
- 守備側を指揮するときは、投手から打者を見る視点を主にする。
- ストライクゾーン、投球位置、球種・球速、打席内の履歴は、必要に応じて展開する。
- 画面表示は投球の物理結果を決めない。

### 2.2 打球後

- 打球がバットに当たった時点で、球場全体を真上から追うカメラへ遷移する。
- 黄色のボールと、直近の移動履歴から作る黄色い尾を描く。
- 野手・走者・送球は、エンジンが確定した時間軸を再生する。表示用の短縮は許すが、結果の再抽選は行わない。
- フライ、ゴロ、壁際、送球、走者の進塁が分かることを優先する。

### 2.3 球場の点描表現

- 球場、選手、フェンス、ボールをドットまたは点線で描けるようにする。
- 座標系はメートル等の実ワールド座標とし、描画側でドット間隔・色・拡大率を変換する。
- 球場の広さ、フェンス高、ファウルゾーン、芝・土、風などは、打球・走塁・守備の物理に反映する。
- それらの数値を速報画面に常時出す必要はない。プレイヤーは打球結果の違いから球場特性を感じる。

## 3. 縦画面の常時情報

画面内にすべてを固定表示せず、情報の優先度で三層に分ける。

### 常時表示するヘッダー

| 領域 | 内容 | 表示規則 |
| --- | --- | --- |
| 試合名 | 対戦チーム・攻守 | 短いチーム名を優先 |
| スコアボード | 1〜9回、`計 / 安 / 失` | 行は先攻・後攻の二行。進行中の回は強調 |
| 状況帯 | 表裏・回・B/S/O・走者 | 最小文字でも誤読しない大きさ |

スコアボードは「合計点だけ」では代用しない。各イニングと `R/H/E` が常に確認できる構成とする。

### 打席カード

| 情報 | 内容 |
| --- | --- |
| 投手 | 背番号、名前、投球腕、主要投手能力 |
| 打者 | 背番号、名前、打席、主要打撃能力 |
| 左右ラベル | **右投 / 右打 = 赤、左投 / 左打 = 青** |
| 履歴 | 打席内の球速・球種・結果を新しい順に表示 |

公開能力はコンパクトにする。心理、迷い、読み、内部成功率などは表示しない。

### 走者表示

走者表示は野球場全体の菱形ではなく、ダイヤ上の一塁・二塁・三塁の三マークだけを用いる。

```text
      二塁

一塁        三塁
```

- 白またはグレーは走者なし。
- 赤の点灯は走者あり。
- ホームを四つ目の走者マークにしない。打者は打席カードで表す。
- 進塁・帰塁中の表示は、アニメーション層でマーク間を移動する。

## 4. 操作面

### 4.1 次打席の主命令

主命令は一行の横スクロール帯に収める。各ボタンは短い語句と種別色だけを表示し、押下時に下部の詳細シートを開く。

```text
[おまかせ] [内角] [外角] [ゾーン] [クサイ] [打たせる] →
```

打撃側も同じ構造にする。

```text
[おまかせ] [中返し] [流す] [引張る] [転がす] [犠飛] →
```

横スクロールは、命令数が多くても画面の高さを圧迫しないために使う。命令そのものは縦スクロールのリストに混ぜない。

### 4.2 開閉する詳細シート

ボタンをタップすると、以下だけを展開する。

- 命令の説明
- 現在の打者／投手との適性
- 実行不能な条件（走者不在の盗塁等）
- 詳細方針: 球種多め、速球多め、敬遠、守備位置、走者警戒

このシートは選択後に閉じ、速報の主画面を維持する。選手成績、守備位置、詳細な打席ログは別の展開領域へ置く。

## 5. 命令がエンジンへ与えるもの

命令は「成功を保証するボタン」ではなく、選手の意図と確率分布を変える入力である。

| 命令例 | 主な影響 | 失敗・副作用 |
| --- | --- | --- |
| 内角中心 | 狙うコース、引っ張り打球の比率 | 甘い球、長打リスク |
| クサイところ | ゾーン境界の狙い、見逃し率 | 四球、球数増加 |
| 打たせてとれ | ゴロ率、変化球選択 | 打球速度・内野の処理負荷 |
| 流し打ち | 打球角度・方向の意図 | 打球速度低下、差し込まれ |
| 送りバント | バント試行、走者のスタート | 失敗、併殺、捕手・投手処理 |
| 盗塁 | リードとスタート閾値 | 牽制死、盗塁刺 |

命令は心理状態を画面に公開しない。心理・読み合いを採用する場合は、隠し能力と打席状況により選手の反応へ反映する。

## 6. 実装上の表示契約

表示層は次の入力だけを受け取る。計算層へ「この視点で再計算して」と要求する API を作らない。

```ts
type MatchPresentationSnapshot = {
  state: CanonicalMatchState;
  events: readonly TimedMatchEvent[];
  camera: "batter" | "pitcher" | "overhead";
  playbackTime: number;
};
```

- `CanonicalMatchState`: 規則・選手・走者・得点の正史状態
- `TimedMatchEvent`: 投球、打球、野手移動、送球、アウト、得点などの時刻付きイベント
- `camera`: 同じイベントの見せ方だけを変える値

この境界を守ることで、画面デザインを変更しても野球結果の再現性を保てる。
