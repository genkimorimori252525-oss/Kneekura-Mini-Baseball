# Action Frontier v1 — headless API

This slice implements the approved world-first live-action boundary from `05-world-first-live-ball-architecture.md` and `06-world-first-runtime-contracts.md`. It does not implement `OfficialPlayClosure`, durable next-play state, UI, or rendering.

## LiveActionFrontier

`createLiveActionFrontier(input)` validates and freezes the current live-work snapshot:

- physical work already in motion;
- committed intents awaiting execution;
- information already causally in flight;
- decisions still pending;
- rule/action windows that require physical live action to remain open;
- each relevant actor's explicit play disposition;
- the canonical event-queue watermark.

Zero velocity is not settlement. An actor is settled only when the actor policy supplies `settled_for_play` with a basis event. Work IDs are unique across categories.

`resolvePlayEndFromFrontier(frontier, terminal?)` returns either `continues` with explicit blockers or `ended` with a `PlayEndFact`.

For quiescent live-ball completion, every live-work category must be empty, all actors must be explicitly settled, and the event queue must be settled through the proposed PlayEnd tick.

For explicit terminal conditions (`dead_ball`, `all_offense_terminal`, or another supported terminal rule event), same-tick event settlement and live-action rule windows still block PlayEnd. Irrelevant post-terminal motion does not.

This API closes physical live action only. Post-play appeal/review/adjudication windows belong to the later `OfficialPlayClosure` boundary.

## EventQueueWatermark

`resolveEventQueueWatermark(currentTick, sources)` combines source-specific settlement claims. Each source reports:

- `settledThroughTick`: no new canonical event at or before this tick remains to be generated by that source;
- `nextPendingTick`: the earliest already-known pending canonical event, or null.

The global watermark is the minimum settled bound, capped at the current canonical tick. A source cannot claim settlement through its own next pending event. Duplicate source IDs are rejected.

The watermark is evidence for finalization; it is not a timer, timeout, or event generator.

## Batting forecast adoption

`battingForecastQueueStatus(forecast, timeline, currentTick)` converts the already accepted batting physical forecast into source settlement evidence without writing canonical history.

`adoptBattingForecastAtTick(forecast, timeline, currentTick)` adopts only at the exact authoritative event tick:

- before the tick -> `WAITING`;
- exact tick -> recompute against the saved commitment and current canonical cursor, then append the existing canonical event batch;
- after the tick -> `MISSED_EVENT`, never backdate;
- already adopted -> `ALREADY_ADOPTED` without another write;
- unresolved physical forecast -> `UNRESOLVED_FORECAST`, and its watermark stays behind unknown future evidence.

Take and swinging-miss outcomes may append a same-tick physical fact plus count adjudication atomically. Contact appends the existing `BatBallContact` event. No fair/foul, runner, scoring, or next-play consequence is guessed here.

## Host responsibilities

The host still owns:

- authentic current source/model/world identity;
- collecting all event-producing sources when computing a global watermark;
- running this adoption at the correct canonical tick;
- globally deduplicating action/event identities;
- updating physical world state and canonical history atomically;
- scheduling/interruption for running, throwing, defense and later live-ball actions;
- ActionFrontier construction from the actual supported actors;
- post-PlayEnd adjudication and `OfficialPlayClosure`;
- persistence and crash recovery.

Pairwise structural equality is consistency checking, not cryptographic authenticity or a persistent exactly-once service.
