# Reserved physical transfer and throw custody

This opt-in extension connects the existing scheduled field throw kernel to the
reserved physical episode. It requires actual secured possession. No release,
catch, target decision, effort value or physical state is invented by the owner.

## Accepted preparation and physical operations

- A new optional `defender_throw` lifecycle calibration binds the existing normal
  fielding model and its original Player/Person to the exact current member and
  all-ten cumulative view. The response explicitly supplies the established
  transfer parameters and throw calibration. Nominal defensive ratings remain
  owned by the normal fielding model.
- `acceptThrowCalibration` uses the existing lifecycle writer's current proof,
  canonical identity, transaction and replay checks. It admits only the optional
  throw route. Historical dispatch routes, exact32 calibration-set acceptance,
  participant coverage and storage schemas retain their existing contracts.
- `throw_plan_v1` accepts only the member/calibration references, original
  defender receiver and bounded command coverage. It retains the full actor
  curves and their actual accelerations, authenticates both defender body poses,
  and uses the episode's original match seed/play plus the plan Source identity.
  Preparation does not advance the ball or sample a future launch.
- `throw_checkpoint_v1` accepts only the original plan reference and an exact
  elapsed horizon. The Core kernel executes pending transfer until the requested
  bound, actual interruption or original release time. It retains custody during
  transfer and interruption; a real release removes carrier custody exactly at
  its release cut and hands ordinary continuation the free-ball cursor.
- Observation and decision steps may interleave without losing pending transfer
  ownership. Competing motion, capture, replacement plans and legacy generic
  field advances are rejected until the original transfer terminates. A released
  or interrupted plan cannot release again.
- A non-launch continuation cannot reuse the old physical predecessor after
  its current view owns an outcome or reset. Only the independent next-pitch
  launch arm may begin the next episode from an accepted reset.
- Continued thrown-ball motion uses the existing field continuation kernel and
  current body coverage. Its ground contacts are not relabeled as the original
  bat-flight first-ground event. This does not add an official fair-ball result.

## Author feedback and remaining integration

`vitest.reserved-throw-custody-author.config.mjs` covers Source shape, accepted
values, actual Core transfer/release/interruption, all-ten composition, current
member and model/Person binding, sensory interleaving, bounded coverage,
large-clock immediate release and free-ball continuation. Normal model and
calibration reads in the composition cases are explicitly mocked. The structural
Core fixtures and calculation tests are not Native SQLite qualification.

`prepareNativePhysicalThrowCalibration` is a dedicated helper for the combined
Native scenario. It accepts explicit fixture values through the normal optional
writer and reconstructs the archived result on a new read-only connection.
IFN01 now also declares two reachable original glove poses before launch and
uses `appendNativePhysicalThrowReception` to request actual scheduled capture,
retained transfer, release, free flight and receiver capture under the original
static curves. Its existing short locomotion checks then start from the actual
receiver cut. No curve is extrapolated beyond its accepted coverage.

A bounded Core probe of the unchanged ordinary swing, these initial poses and
the same explicit effective throw/retention values reached both secured captures
and the intervening release. This is feasibility evidence, not Native
qualification. The extended IFN01 scenario has not been run in this component's
author lane; the combined source still needs its consolidated compiler,
independent review and genuine Native scenario.

Actual capture remains a prerequisite to throw admission. Production of
fatigue-response or contextual receiver-selection Sources, operation-aware
controller renewal during a pending transfer, runner/base/tag fact integration
and fair-ball terminal adjudication remain explicit product boundaries. No new
numerical calibration, fatigue/score formula or autonomous policy is selected.
