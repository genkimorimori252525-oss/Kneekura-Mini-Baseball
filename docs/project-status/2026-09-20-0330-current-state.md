## 2. Overall state

The project is currently best described as:

> **A broad, deterministic baseball Match Core and renderer-neutral observation foundation, not yet a complete playable season game.**

The Core already contains substantial causal pitching/contact/fielding/running/rules/manager-command machinery. The largest remaining gaps are general live-ball orchestration across arbitrary multi-runner plays, official adjudication/closure, complete official scoring, the actual finished game client/UI, and most career/world systems.

The repository currently has no normal game-client `start`/`dev` runtime in `package.json`; the implementation branch is primarily TypeScript Core/Presentation contracts plus Vitest acceptance/regression tests.

## 9. Design ownership and fixed direction

### 9.1 Work owns visual/product design

Work向けの正式なPresentation brief:
`docs/presentation/2026-09-20-work-handoff-drone-art-broadcast-camera.md`

その中心定義は、**「正史の数値野球世界を、Drone-Art＋4px＋55msの意図的に粗い中継カメラで観測する」**である。粗さは暫定品質ではなく、完全3D描画より軽い観測層を採用する製品思想である。

As of this record, **ChatGPT Work owns UI/UX, visual/art direction, screen composition, Presentation styling, and player-facing visual design work**.

Coding agents should not invent visual alternatives simply because a renderer or prototype is missing.

Their boundary is:

```text
approved Core / canonical state
        ↓
renderer-neutral Presentation contract
        ↓
approved Work design
        ↓
implementation
```

If the Work design does not exist for a requested surface, an implementation agent should preserve the data seam rather than choose a new design direction.

### 9.2 Direction already fixed enough to preserve

The following is already established and should be treated as a constraint for Work and implementation alike unless explicitly revised:

- **world-first**, not result-first;
- **Presentation is an observer**, never baseball-result authority;
- **ASCII is not the current product direction**;
- **Drone-Art is a confirmed Mini visual direction to be handed to Work**;
- **4px fixed display grid and 55ms standard Presentation cadence are confirmed Work design requirements**, while remaining strictly outside Match Core physics authority;
- offensive at-bat view uses the **Batter POV** role;
- defensive/pitcher-operation view uses the **catcher-behind Pitcher POV** role;
- fair-ball/live field action transitions to a **field/overhead observation** role;
- lightweight/minimal representation is allowed, but the exact visual language/polish is a design decision, not a Core rule;
- **Simple Surface / Deep Simulation** remains the product-level intent: deep internal causality should not force a complicated player-facing surface;
- Mini and future Natural observe the **same Match Core**.

### 9.3 Current source precedence for Presentation/design

Use newer authority before older prototypes:

1. latest explicit user decision / approved Work handoff;
2. `docs/game-design/05-world-first-live-ball-architecture.md`;
3. `docs/game-design/03-roadmap.md` and P8 canonical observer/acceptance documents;
4. current manager-experience/design handoff where not superseded;
5. older fixed-fixture Batter POV prototypes only as historical reference; the current Drone-Art/4px/55ms requirements themselves are not legacy.
