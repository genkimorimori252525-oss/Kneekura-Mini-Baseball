# Feedback loop — 成果から改善する

## 収集源は分ける

- 自動観測: `PostToolUseFailure`フックが`.claude/feedback/events.jsonl`に「ツール失敗を観測した」という事実だけ記録。Stopフックが「応答終了」を記録。
- 実績: `/finish-task`でタスクの成功/部分成功/失敗、実際に通したテスト、手戻り、結果が分かれば時間/費用を記録。
- 本人のフィードバック: `/record-feedback`で明示された良かった点・問題点をローカルに記録。
- 正式な問題: `/report-bug`によって検証し、ローカルIssueを準備。GitHubへの送信とは完全に分ける。

**観測と結論を混同しない:** `PostToolUseFailure`が5件あることは、製品バグが5件あることを意味しない。`Stop`が10回あることは、タスク成功10回を意味しない。

## 自己改善の手続き

1. 最低数件の具体的な失敗、または明白な一件の重大な欠陥を集める。
2. 原因分類: 仕様漏れ、テスト不足、モデル選択、委任境界、コンテキスト不足、環境・依存関係、外部障害。
3. `summary` とログを確認して改善仮説を1つだけ立てる。
4. 利点・副作用・検証方法・ロールバックを文書化し、ユーザーに提案する。
5. **承認後**に最小限のCLAUDE.md/Skill/Hook/Testを変更する。
6. 近い条件で再テストする。否定された仮説は撤回する。
7. 反証可能な学びだけ`LESSONS.md`に残す。永続メモリの肥大化を避ける。

## 改善提案の短いテンプレート

```text
課題: 同じ型の修正でテスト漏れが2回発生
証拠: TASK-XX、TASK-YY（具体的なログと差分）
原因候補: テストを実装終了時に要求する規則が曖昧
変更案: finish-task Skillに検証コマンドの実行確認を1行追加
期待効果: 未実施テストの発生率低下
危険: 軽微な文書編集にも不要な検証が増える
検証: 次の同種5件で未実施テスト件数を比較
撤回条件: 余計な検証時間だけ増えて改善しない
承認: 未取得
```

## プライバシー

ローカル観測にはrawコマンド、会話全文、環境変数、実行ログ本文、秘密文字列を記録しない。フィードバックは意図的な短いコメントだけ。プライベートIssueでも内容の読み直しが必要。これらのローカル記録は`.gitignore`で対象外にする。
