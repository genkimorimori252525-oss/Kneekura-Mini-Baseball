# Model routing — Opusを中心に必要なときだけ委任

## 基本方針

推奨初期値は **メインOpus 5.5 Medium**。Opusが複数ファイルにまたがる設計、依存関係、最終受け入れを担当する。作業が小さい/密結合ならOpusが自分で作業した方が安定しやすい。

| タスク条件 | デフォルト | 理由 | 代替 |
|---|---|---|---|
| 変更1〜2ファイル、軽微、依存関係が密 | メインOpus direct、medium | 委任の起動と受け渡しが無駄 | 本体を手動でSonnetへ変更できるが、必須ではない |
| 独立・境界明確・通常実装 | Opus計画→Sonnet 5.5実装、medium→Opus確認 | コンテキストを分離して経済的な可能性 | Sonnetの手戻りが多ければOpus直接 |
| 独立の簡易リサーチ | Haiku 5.5 scout、low→Opus統合 | 大量探索結果を本体へ流し込まない | 難問はOpus自分で調査 |
| 障害の根本原因・複雑な改修 | Opus 5.5 direct/high またはOpus specialist/high | 精度と検証の優先 | Sonnetで解決済みなら委任不要 |
| 分離可能な複数機能の実装 | 最初は書込みworker1、必要なら分離worktreeで2 | 並列で実利益がある場合だけ | 同じファイルに触るなら直列 |
| システム全体の設計・敵対的監査 | メインOpus high、必要なら独立Reviewer | 難しい判断の品質優先 | xhigh/maxは評価上の利得確認後 |

## モデル選択はどう実装されるか

`.claude/agents/*.md` の `model:` と `effort:` は各サブエージェントに対する設定。メインモデルは `.claude` 定義だけで自動的に切り替わらない。`/model`と`/status`で手動確認する。サブエージェント実行中は`/tasks`でモデル表示を確認する。

Claude Codeには `/model opusplan` という、計画時Opus→実装時Sonnetへ自動切替する公式の簡易ハイブリッド方式もある。**これは独立したサブエージェントへ実装委任する方式とは異なる**。小型プロジェクトやコンテキストが一つで十分な場合は、むしろ `opusplan` が簡単な候補になる。

### 明確な分担契約

Opusからworkerに渡す依頼は、対象パス、触らないファイル、依存関係、入力/出力、検証コマンド、Doneの条件、停止条件、モデル名をセットで指定する。成果を受け取ったら実際のdiffとテスト結果を確認する。検証できない場合は進捗を完了扱いにしない。

### 失敗時のエスカレーション

1. 独立した修正タスクをSonnetが失敗したら、テスト結果と仮説を整理する。
2. 同じ問題に対するSonnetの再試行は原則1回まで。失敗が残ればOpusで原因を再評価する。
3. 主原因が設計の誤りか、仕様の曖昧さか、ツールや環境の異常かを区別する。
4. 再現した不具合はローカルIssue下書きへ。改善効果は実測する。

## Effortとキャッシュ

Opus 5.5の標準Effortはmedium。highは難しい作業のため、xhigh/maxは利益を実測できる場面だけ。APIではトップレベルeffortの変更がプロンプトキャッシュに影響し得る。Claude Codeの環境とバージョンごとの挙動は公式仕様を確認する。

## 重要な比較上の注意

モデルの単価を比較して「総使用量」を推定しない。実際にはツール往復、キャッシュ再読み込み、やり直し、統合作業が関わる。Sonnetに移した方が安い案件も、Opusの一発修正が安い案件もある。比較は `05_EVALUATION.md` に沿って行う。
