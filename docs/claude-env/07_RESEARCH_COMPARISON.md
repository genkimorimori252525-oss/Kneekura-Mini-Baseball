# 詳細比較 — Opus 5.5単独 vs Opus司令塔+サブエージェント

調査日: 2026-11-02。数値は各資料の報告値であり、このパック自身のベンチマーク結果ではない。

## 観察・研究結果

| 資料 | 何を比較したか | 見つかったこと | この設計への影響 |
|---|---|---|---|
| Anthropic Multi-agent research system (2025) | 大規模調査における単独/複数エージェント | 複数エージェントは多くのトークンを使う。通常チャットに対して単独agent約4倍、multi-agent約15倍という説明。コーディングは研究ほど並列化しづらい | コーディング用に固定の大人数チームを使わない |
| Google Research (2026) | 180構成のマルチエージェント設計、領域別 | 並列化可能なタスクでは利益、逐次依存タスクでは明確な性能悪化 | 独立した仕事に限定してworker投入 |
| MIT Media Lab / Nature Machine Intelligence | 260構成、6ベンチマーク、5アーキテクチャ | 高性能単独agentでは、協調の追加利益が減少/逆転することがある | Opus単独を有力なベースラインとして保持 |
| Anthropic cost/intelligence guide | 限られた大規模ワークロードのmulti-model orchestrator | 一部の条件でコスト約半減・速度向上の一方、成功率が約10〜12ポイント低下した測定例。一般的な全コーディングタスクに直接当てはまらない | 合格率を犠牲にして見かけの安さだけを追わない |
| Reddit 個人実験、27 Sonnet 5 vs 27 Opus 5.5 | Opus 5.5 main＋それぞれの実装worker | Sonnet 5 workerの中央値14分・90 tool calls・$2.20、Opus 5.5 workerの中央値9分・40 calls・$1.10。作業バッチが異なり厳密な比較ではない | 難問ではworker自体をOpusにした方が安くなる可能性 |
| Reddit Opus 5.5計画+Sonnet 5.5実装 | 個人のMaxプラン使用枠体験 | 以前の2〜3倍長持ちしたという報告。他の施策も同時変更され、効果の切り分けは不可能 | 適度な難易度の独立実装でハイブリッドを試す |
| Reddit Opus main + Sonnet worker、両方Max Effort | 個人のAndroid画面実装 | 中規模と称する仕事に約9時間。過剰な高Effortと再試行が不利の可能性 | workerのEffort medium、必要な時だけhighにする |

**研究の数え方:** Google Researchの180構成の報告とMIT Media Labの260構成の報告は関連する研究の異なる段階・掲載情報であり、独立した二つの実験として水増ししない。

## 判断

**どちらか一択ではない。最適な初期運用は「Opus 5.5単独を原則とし、独立した通常実装の時だけOpus司令塔＋Sonnet 5.5実装」にする条件付きハイブリッド。**

根拠:

1. 現在のOpus 5.5は単独で複雑なコード変更を処理する能力が高い。複数人の調整は性能を必ず上げない。
2. 必要な仕事だけ別のコンテキストへ出すと、本体の文脈汚染を減らし、並列化や小モデル利用による利点を狙える。
3. ただし実際の費用は修正成功率・再試行・キャッシュ再読込で逆転する。Sonnetが安価というだけでは結論は出せない。
4. ローカルで本当に同一課題の比較をして、使い分けの境界を調整する方が、固定チームより反証可能で堅牢。

## 再評価すべき条件

- 大きなアーキテクチャ変更を含むワーカータスクで何度も差し戻しが起きる → Opus worker / directの比率を上げる。
- 大量の相互独立した実装で待ち時間が長い → 分離worktreeを使った2 workerを検証する。
- 小規模タスクばかりでサブエージェント起動が頻繁 → main directに戻す。
- 予算圧迫があり、品質に問題がない → 小型worker / effort lowを限定試験。
- 独立研究/資料収集が大量 → Haiku scoutの出力をOpusが精査する。
